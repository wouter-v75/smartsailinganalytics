# Reviewing drone footage without moving it

*What Njord actually does, what the broadcast industry does, and what SSA should
do. 1 October 2026.*

The ask: plug the SSD in, **quickly** review the day's drone footage on the
laptop, drop `Grab video` tags where something is worth keeping, then cut and
upload only those. Today the review step does not exist — the footage is only
ever seen by `ffmpeg`, and the tags are pressed on the water or guessed at
afterwards.

---

## 1. What Njord does

Njord Player is a **desktop application**, and its project file (`.sail2`) holds
**reference paths**, not video. The behaviour gives it away:

- Move the files and the affected clips "show up in red in the timeline and
  cannot be played", with a **Locate Files…** button to re-point them.
- Re-association is by **filename**: "file names must be identical to what they
  were when adding the file", and Njord "extracts timestamps from filename
  patterns — renaming files before loading may prevent correct automatic
  timestamp detection".
- Their advice is to keep the `.sail2` beside the video, one folder per day, and
  move the whole folder as a unit.

So: **the project stores a path, a filename and a timestamp. The video stays on
the disk it was always on.** Nothing is uploaded to review it. That is the whole
trick, and it is not a clever compression — it is simply declining to copy.

Their DJI advice matches ours: keep the `.SRT` sidecars, which is how the player
"accurately detect[s] file timestamp offsets that may be present in DJI video
files". SSA already parses those — the 30 September run reported *"SRT: 11 of 11
clips timed from their sidecar · they place the first frame 0.29–1.05 s from the
file's own stamp"*.

## 2. The same idea, industrially

This is the standard media-asset-management shape, and iconik states it plainly:
it "indexes your content and creates lightweight proxies and metadata in the
cloud, but your original files stay exactly where they are: on-prem, in the
cloud, or both — no redundant uploads, no wasted storage, and no accidental
duplication."

Three properties are worth stealing, and only three:

| | |
|---|---|
| **Index, don't ingest** | The catalogue holds a path, a time, a duration and a thumbnail. Originals never move. |
| **Proxies for everything you look at** | "Lightweight copies generated on ingest so footage is browsable without pulling originals across the network." |
| **Metadata at a TIMECODE, not at a file** | "Organization and tagging happen at a timecode or clip range rather than only at the file level." |

SSA already has the third — that is what `ssa_tag_events` is — and the first in
part, via the new `drone_coverage`. The missing piece is the second.

## 3. The lever nobody is using: the proxies are already on the card

**DJI writes a 720p proxy next to every clip, automatically.** The `.LRF` files:
H.264, 1280×720, roughly 7–8 Mbit/s, generated by the camera during recording,
and used by the controller for playback precisely because they "load faster and
require less processing power".

Against a 4K clip at ~250 Mbit/s that is about **a thirtieth of the bytes**. The
30 September card held 11 clips totalling 5.2 GB over 25 minutes of filming; the
LRFs for the same footage would be roughly 150 MB.

Two consequences:

- **No transcode step.** The usual proxy workflow's cost is making the proxies.
  Here the camera already did it, at record time, for free.
- **They are already on the SSD** — and SSA ignores them. `select-race-clips.mjs`
  scans `.mp4/.mov/.m4v` only, so `.LRF` is invisible to every script we have.

**First thing to check:** `ls /Volumes/SSK\ SSD/20260930/Drone/*.LRF`. If they
are there, the fast review is nearly free. If they are not, the camera setting
that makes them is the single highest-value change to the filming routine, and
costs nothing on the card.

## 4. How SSA should do it

The constraint that decides everything: **SSA is a web app and the footage is on
a USB disk.** Two honest ways across that gap.

### Option A — the browser reads the disk directly

The File System Access API lets a page hold a handle to a directory, and the
handle survives in IndexedDB, so "a returning user can reopen the same local
file without selecting it again". Point SSA at `/Volumes/SSK SSD/20260930/Drone`
once; thereafter it opens the folder itself.

- **For:** no second process, no port, no install. Exactly the "Watch clips"
  pattern already in the Upload tab, which the crew have used all week.
- **Against:** Chrome and Edge only — **not Safari, not Firefox**, which "ship
  only OPFS". On a Mac that means the review tab must be Chrome.

### Option B — a one-line local media server

`npm run media:serve` opens a tiny HTTP server on the SSD folder with byte-range
support; SSA plays `http://localhost:7777/DJI_…_D.LRF`.

- **For:** every browser, Safari included. Range requests give real scrubbing.
  The same server can list the folder, so the coverage scan and the review share
  one source of truth.
- **Against:** a second thing to start, and a port. It is another terminal
  window in a workflow that already has three.

### Recommendation

**Option A, with the LRF as the thing it plays.** It matches how the crew
already work (point the watcher at a folder once, forget it), needs nothing
running, and Chrome is already on the machine — `docs:pdf` drives it. Option B
is the fallback if the review ever needs to happen on an iPad.

And **do not store the video in SSA**, in either case. Store what Njord stores:
the folder handle, the filename, the start time, the duration. The clips that
get cut are already uploaded; the originals stay on the SSD and the archive
drive, where they belong.

## 5. The workflow this produces

1. Plug in the SSD. `npm run drone:coverage -- <date> --write` — already built;
   the track shows light green where there is footage.
2. Open the Tags tab. Press **Review footage**, pick the day's folder once.
3. The track's green bands become playable: click one, the LRF plays from that
   second. Scrubbing is instant because it is 720p off a local SSD.
4. Space to play/pause, **G** to drop a `Grab video` tag at the playhead. This is
   what every tagging tool does — OpenTag.Studio gives "all buttons an optional
   keyboard shortcut… set to single characters", TagPlay tags "with keyboard
   shortcuts while watching… without pausing". One key, no dialog.
5. `npm run clips:day -- <date> --gybes --write` cuts from the **4K originals**,
   as now. The proxy was only ever for looking at.

Steps 2–4 are the new part. Everything else exists.

## 6. What this does not fix

- **It does not make the footage available to the team.** Only the cut clips go
  to Bunny. That is the intent — reviewing 5 GB to choose 300 MB is the whole
  point — but it means the review step happens on the one machine with the disk.
- **It does not survive the disk being unplugged.** The handle goes stale and the
  bands become un-clickable. Njord shows those clips in red and offers *Locate
  Files…*; SSA should do the same rather than failing silently.
- **It is not an editor.** No trimming by hand, no reordering. The cutter's
  windows stay the mechanism.

## 7. Effort

| | |
|---|---|
| Teach the scripts about `.LRF` (scan, pair to its `.MP4`, prefer for review) | small |
| Folder handle in `ssa-prefs`, with a re-pick path when it goes stale | small — `prefsStore.js` exists for exactly this |
| A review pane in the Tags tab: play the proxy, seek from the track, one-key tag | the real work |
| Stale-media state, the red-clip equivalent | small, and the thing that stops it feeling broken |

The risk worth naming: **`DB_VER`**. The folder handle is a preference, not a
day's data, so it goes in `ssa-prefs` — see the note in `CLAUDE.md` about what
moving `ssa-db`'s version did to video playback for an evening.
